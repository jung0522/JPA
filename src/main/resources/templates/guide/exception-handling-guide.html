예외 처리 가이드

Spring Boot 전역 예외 처리 및 에러 응답 표준화

🔄 예외 처리 흐름도

1

Controller에서 예외 발생

throw new BusinessException(ErrorCode.USER_NOT_FOUND)
2

Exception Handler가 예외를 캐치

REST API: RestApiExceptionHandler (@RestControllerAdvice)
MVC 웹: MvcExceptionHandler (@ControllerAdvice)

3

ErrorCode에서 메시지 키 추출

errorCode.getMessageKey() → "error.user.not.found"
4

MessageSource에서 다국어 메시지 조회

messages.properties: "사용자를 찾을 수 없습니다."
messages_en.properties: "User not found."

5

로깅 (개발자용 상세 정보)

log.warn("[BusinessException] code=USER001, detailMessage=..., args=...")
6

클라이언트에 응답

JSON (API): {"code": "USER001", "message": "사용자를 찾을 수 없습니다."}
HTML (WEB): error.html 페이지 렌더링

💡 핵심: 개발자는 상세 로그를 보고, 클라이언트는 사용자 친화적인 메시지를 받습니다.

🎯 @RestControllerAdvice vs @ControllerAdvice

@RestControllerAdvice

대상

@RestController 전용

응답 형식

JSON (자동으로 @ResponseBody 적용)

적용 패키지

io.goorm.jpa.controller.api

반환 값

ResponseEntity<ErrorResponse>

사용 예시

@RestControllerAdvice(
  basePackages = "io.goorm.jpa.controller.api"
)
public class RestApiExceptionHandler {

  @ExceptionHandler(BusinessException.class)
  public ResponseEntity<ErrorResponse> handle(...) {
    return ResponseEntity
      .status(e.getErrorCode().getHttpStatus())
      .body(ErrorResponse.of(...));
  }
}

@ControllerAdvice

대상

@Controller 전용

응답 형식

HTML (View 이름 반환)

적용 패키지

io.goorm.jpa.controller.web

반환 값

String (View 이름)

사용 예시

@ControllerAdvice(
  basePackages = "io.goorm.jpa.controller.web"
)
public class MvcExceptionHandler {

  @ExceptionHandler(BusinessException.class)
  public String handle(..., Model model) {
    model.addAttribute("errorMessage", ...);
    return "error/error";  // HTML 템플릿
  }
}

⚠️ 주의사항

basePackages를 반드시 지정하세요!

만약 둘 중 하나만 있고 basePackages를 지정하지 않으면, @RestController와 @Controller 모두 처리하게 됩니다. 이는 의도치 않은 동작을 유발할 수 있습니다.

📝 로깅 설정 가이드

Exception Handler는 개발자용 상세 로그를 남기고, 클라이언트에게는 사용자 친화적인 메시지를 전달합니다.

로깅 레벨별 차이

WARN

비즈니스 예외 (복구 가능)

사용자 입력 오류, 권한 없음 등

log.warn("[BusinessException] code={}, detailMessage={}, args={}",
    e.getErrorCode().getCode(),
    e.getDetailMessage(),
    e.getArgs() != null ? Arrays.toString(e.getArgs()) : "none");

Stack Trace: 출력하지 않음 (경고성 메시지만)

ERROR

시스템 예외 (복구 불가)

DB 연결 실패, 예상치 못한 에러 등

log.error("[DataAccessException] type={}, message={}",
    e.getClass().getSimpleName(),
    e.getMessage(),
    e);  // 마지막에 예외 객체 전달 → Stack Trace 출력

Stack Trace: 자동 출력 (문제 분석에 필수)

application-jpa.properties 로깅 설정

# 로깅 레벨 설정
logging.level.root=INFO
logging.level.io.goorm.jpa=DEBUG                           # 우리 애플리케이션 로그
logging.level.org.hibernate.SQL=DEBUG                      # SQL 쿼리
logging.level.org.hibernate.type.descriptor.sql.BasicBinder=TRACE  # SQL 파라미터
logging.level.org.springframework.security=DEBUG           # Security 로그
logging.level.org.springframework.web=DEBUG                # Web 요청/응답 로그

# 로그 출력 패턴 (시간, 스레드, 레벨, 로거명, 메시지)
logging.pattern.console=%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n

로그 레벨별 의미

  • ERROR 즉시 조치 필요 (Stack Trace 포함)
  • WARN 경고 (Stack Trace 없음)
  • INFO 주요 이벤트 (서버 시작, 종료 등)
  • DEBUG 개발 중 디버깅 정보
  • TRACE 매우 상세한 정보 (SQL 파라미터 등)

💡 실무 팁

  • • 개발 환경: DEBUG 레벨 사용 (상세 로그)
  • • 운영 환경: INFO 레벨 사용 (필요한 것만)
  • • 문제 발생 시: 일시적으로 DEBUG로 변경 후 분석
  • • TRACE 레벨: SQL 파라미터 확인 시에만 사용 (성능 영향)

🧪 예외 처리 테스트하기

현재 프로젝트에서 제공하는 테스트 방법:

1. Swagger UI로 잘못된 로그인 시도

① Swagger UI 열기

② POST /api/auth/login 선택

③ 존재하지 않는 사용자로 로그인 시도:

{
  "username": "notexist",
  "password": "1234"
}

④ 응답 확인:

{
  "code": "USER001",
  "message": "사용자를 찾을 수 없습니다."
}

⑤ 서버 로그 확인:

2025-01-15 14:23:45.123 [http-nio-8080-exec-1] WARN  i.g.j.e.RestApiExceptionHandler - [BusinessException] code=USER001, detailMessage=null, args=none

2. 잘못된 비밀번호로 로그인 시도

① POST /api/auth/login

② 올바른 username, 잘못된 password:

{
  "username": "admin",
  "password": "wrongpassword"
}

③ 응답 확인:

{
  "code": "USER004",
  "message": "비밀번호가 올바르지 않습니다."
}

📋 정의된 ErrorCode 목록

✅ 현재 사용 중

USER001

사용자를 찾을 수 없습니다

USER004

비밀번호가 올바르지 않습니다

COMMON001

서버 오류가 발생했습니다

AUTH001~003

인증 관련 오류

📌 향후 확장 예정

BOARD001~002

게시판 관련 오류

COURSE001~003

강의 관련 오류

ENROLLMENT001~004

수강신청 관련 오류

CONCURRENCY001~002

동시성 제어 오류

💡 설계 의도: 실무에서는 에러코드를 미리 정의해두고 필요할 때 사용합니다. Backbone 단계에서 모두 정의해두면, 이후 기능 확장 시 일관된 에러 처리가 가능합니다.
