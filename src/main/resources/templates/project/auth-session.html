🔐 인증 방식 변경

JWT 토큰 → 세션 기반 인증으로 전환

Tag: html-jwt-problem

❌ JWT + Thymeleaf 조합의 문제점

1. 페이지 네비게이션 문제

상황:

  • 로그인 성공 → JWT 토큰이 localStorage에 저장됨
  • 헤더에서 JavaScript로 로그인 상태 확인 → "사용자명 (역할) | 로그아웃" 표시
  • 메뉴에서 "강의" 클릭 → <a href="/course"> 일반 링크로 페이지 이동
  • 문제 발생: 일반 링크 클릭 시 HTTP 요청에 Authorization 헤더를 포함할 수 없음

결과:

  • 페이지 컨트롤러에 인증 필요 → AUTH003 인증이 필요합니다 에러
  • 페이지를 permitAll()로 열기 → 빈 페이지가 먼저 보임 → JavaScript에서 requireLogin() 체크 → 로그인 페이지로 리다이렉트

2. JWT 토큰의 근본적인 한계

JWT는 왜 이런 문제가 생기나?

  • localStorage는 JavaScript에서만 접근 가능
  • 일반 HTML 링크 (<a href>)는 브라우저가 직접 처리 → JavaScript 개입 불가
  • HTTP 요청 헤더를 수동으로 추가할 수 없음
  • 모든 페이지 이동을 JavaScript로 처리해야 함 (SPA 방식 강제)

3. 어중간한 아키텍처

JWT + Thymeleaf는 서로 맞지 않는 조합:

JWT가 적합한 환경

  • SPA (React, Vue, Angular)
  • 클라이언트 라우팅 (페이지 이동 없음)
  • 모든 통신이 API 호출
  • Stateless 서버

Thymeleaf가 적합한 환경

  • 전통적인 MVC 패턴
  • 서버 사이드 렌더링
  • 페이지 이동 = 서버 요청
  • 세션/쿠키 기반 인증

✅ 해결 방안: 세션 기반 인증

세션 기반 인증의 장점

  • 자동 쿠키 전송: 브라우저가 모든 요청(페이지, API)에 자동으로 쿠키를 포함
  • 일반 링크 작동: <a href="/course"> 클릭 시에도 인증 정보 전달
  • fetch API 호환: 같은 도메인이면 fetch 호출 시에도 자동으로 쿠키 포함
  • Authorization 헤더 불필요: 수동으로 토큰 관리할 필요 없음
  • Spring Security 기본 방식: 세션은 Spring Security의 전통적이고 검증된 방법

변경 사항 요약

항목 JWT (이전) 세션 (변경 후)
인증 정보 저장 localStorage 서버 세션 + 쿠키
전송 방식 Authorization: Bearer {token} Cookie: JSESSIONID={sessionId}
페이지 링크 ✗ 작동 안 함 ✓ 자동 작동
fetch API 수동으로 헤더 추가 ✓ 자동 쿠키 전송
로그인 상태 확인 localStorage.getItem('token') 서버에서 자동 확인
Spring Security 커스텀 필터 필요 ✓ 기본 지원
Auditing ✓ 작동 ✓ 작동

🔧 구현 세부사항

1. 제거할 파일/코드

삭제 대상:

  • src/main/java/io/goorm/jpa/config/jwt/JwtTokenProvider.java
  • src/main/java/io/goorm/jpa/config/jwt/JwtAuthenticationFilter.java
  • src/main/java/io/goorm/jpa/config/jwt/JwtAuthenticationEntryPoint.java
  • application.yml의 jwt.* 설정

수정 대상:

  • SecurityConfig.java - JWT 필터 제거, 세션 정책 변경
  • AuthService.java - JWT 토큰 발급 제거, 세션 기반 로그인으로 변경
  • 프론트엔드 - localStorage 사용 제거

2. SecurityConfig 변경 포인트

Before (JWT):

.sessionManagement(session -> session
    .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
)
.addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)

After (세션):

.sessionManagement(session -> session
    .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
    .maximumSessions(1)
    .maxSessionsPreventsLogin(false)
)

3. 로그인 API 변경

Before (JWT 토큰 발급):

String token = jwtTokenProvider.createToken(user.getUserNo(), username, user.getRole());
return LoginResponse.builder()
    .token(token)
    .username(username)
    .role(user.getRole())
    .build();

After (세션 저장):

Authentication authentication = new UsernamePasswordAuthenticationToken(
    user.getUserNo(), null, List.of(new SimpleGrantedAuthority(user.getRole().name()))
);
SecurityContextHolder.getContext().setAuthentication(authentication);
// Spring Security가 자동으로 세션에 저장

return LoginResponse.builder()
    .username(username)
    .role(user.getRole())
    .build();

4. 프론트엔드 변경

Before (localStorage + Authorization 헤더):

// 로그인 성공 시
localStorage.setItem('token', result.data.token);
localStorage.setItem('username', result.data.username);

// API 호출 시
const token = getToken();
fetch('/api/boards', {
    headers: { 'Authorization': 'Bearer ' + token }
});

After (쿠키 자동 전송):

// 로그인 성공 시 - 토큰 저장 불필요
// 서버가 자동으로 세션 생성 및 쿠키 발급

// API 호출 시 - 헤더 추가 불필요
fetch('/api/boards', {
    credentials: 'include'  // 같은 도메인이면 생략 가능
});

📌 중요 사항

✓ Spring Security는 그대로 유지

세션 기반 인증도 Spring Security를 사용합니다. @PreAuthorize, SecurityContext 모두 동일하게 작동합니다.

✓ Auditing도 문제없음

AuditorAware는 SecurityContextHolder에서 인증 정보를 가져옵니다. JWT든 세션이든 동일하게 작동합니다.

✓ fetch API 사용 그대로

현재 프론트엔드 구조(fetch로 API 호출)는 그대로 유지됩니다. Authorization 헤더만 제거하면 됩니다.
